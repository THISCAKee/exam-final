# Vercel deployment plan

Goal: Deploy the existing 80-question exam on the user's Vercel Hobby account without losing the single-attempt lock or Google Sheets export.

Architecture: Keep SQLite for local development and add Turso/libSQL HTTP storage for Vercel. Both execute the same transactional attempt logic with unique name/ID constraints. Use request-driven expiry, Next.js after() for result delivery, and a protected daily Hobby cron as a fallback when no students remain online. Anuphan stays bundled locally.

Choice: Turso preserves the existing SQLite schema and provides durable remote storage. Postgres/Neon would require a separate SQL implementation and data conversion. This implementation choice is made by the agent for the requested deployment, not an additional user requirement.

- [ ] Add HTTP transport tests for bound parameters, baton transactions, rollback, errors and connection closure.
- [ ] Make the existing attempt store asynchronous over a shared SQL transport and rerun all single-attempt tests.
- [ ] Wire Vercel database configuration, awaited request writes, post-response export and authenticated cron. Do not use a local database fallback on Vercel.
- [ ] Prepare a migration that preserves all existing local attempts and synced flags without deleting local data.
- [ ] Run tests, type checking, lint, production build and compiled API smoke tests.
- [ ] Provision Turso and Vercel only after the required agreement/access confirmation. Migrate the existing local attempt with explicit confirmation for that data destination.
- [ ] Publish sanitized source and configure production secrets. Verify the live deployment and the single-attempt flow using clearly marked disposable QA identities, never real student submissions.

Constraints: Do not publish credentials, .data, private student records or node_modules to GitHub. A protected cron may run daily on Hobby; inactive crashed sessions can be exported on later requests or the next cron, while re-entry is always blocked by the durable reservation from the start. Preview deployments must not share the production database.
